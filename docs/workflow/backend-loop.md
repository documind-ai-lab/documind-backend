# 백엔드 개발 루프

## 목적

DocuMind 백엔드는 프로젝트별 문서, 대화, 분석 결과, 근거, 리스크 후보를 안정적으로 다루는 업무용 API 서버다. 이 문서는 백엔드 작업을 이슈 단위로 작게 나누고, 설계와 검증 기준을 일관되게 반복하기 위한 개발 루프를 정의한다.

백엔드 작업의 기본 목표는 기능을 빠르게 추가하는 것보다, 서비스 규모가 커져도 API 계약과 서비스 경계가 흔들리지 않게 만드는 것이다.

## 기본 원칙

- 이슈 하나는 PR 하나로 끝낼 수 있는 크기로 나눈다.
- 구현보다 API 계약과 데이터 흐름을 먼저 정리한다.
- 도메인 규칙은 라우터나 외부 연동 코드에 흩어두지 않는다.
- 외부 시스템은 포트 인터페이스 뒤에 둔다.
- 완료 판단은 코드 작성 여부가 아니라 검증 증거 기준으로 한다.

## 백엔드 작업 루프

### 1. 목표 정리

작업을 시작하기 전에 이슈에서 다음 내용을 확인한다.

- 어떤 사용자 문제를 해결하는가
- 어떤 API, 도메인, 저장소, 외부 연동이 영향을 받는가
- 이번 작업에서 제외할 범위는 무엇인가
- 완료 후 무엇으로 검증할 수 있는가

목표가 흐리면 바로 구현하지 않고 이슈 내용을 먼저 정리한다.

### 2. 서비스 경계 확인

백엔드는 기능 이름이 아니라 책임 경계를 기준으로 나눈다.

- `projects`: 프로젝트 생성, 조회, 설정 관리
- `documents`: 문서 업로드, 텍스트 추출 상태, 문서 메타데이터 관리
- `analysis`: 견적서, 제안서, 계약서, 회의록 분석 요청과 결과 관리
- `evidence`: 답변 출처, 문서 인용, 관련도, 근거 연결 관리
- `memory`: 프로젝트별 결정사항, 리스크 후보, 장기 맥락 관리
- `chat`: 사용자의 대화 요청을 분석 흐름으로 연결하는 인터페이스

`chat`은 제품의 중심 도메인이 아니라 사용자가 AI 분석 기능에 접근하는 진입점으로 본다.

### 3. API 계약 작성

구현 전에 API 계약을 먼저 정한다.

계약에는 다음 항목을 포함한다.

- HTTP method와 path
- 요청 파라미터와 요청 본문
- 응답 본문
- 오류 응답
- 인증 또는 프로젝트 접근 조건
- 비동기 처리 여부
- 프론트엔드가 화면 상태를 표현하는 데 필요한 필드

API 응답은 화면에 필요한 값을 숨기지 않는다. 예를 들어 문서 처리 상태가 필요하면 `status`, `progress`, `failedReason`처럼 화면이 그대로 사용할 수 있는 필드를 제공한다.

### 4. 테스트 기준 정리

작업 유형에 따라 필요한 테스트를 선택한다.

- 라우터 작업: 요청/응답 스키마, 상태 코드, 오류 응답 테스트
- 유스케이스 작업: 도메인 규칙, 분기, 예외 상황 테스트
- 저장소 작업: 데이터 저장, 조회, 정렬, 필터 조건 테스트
- 외부 연동 작업: 포트 인터페이스 기준의 어댑터 테스트와 실패 처리 테스트
- 문서 작업: 금지 표현 검색, 목차와 완료 기준 확인

테스트가 아직 준비되지 않은 초기 단계라도, 어떤 방식으로 검증했는지 PR 본문이나 커밋 본문에 남긴다.

### 5. 구현

구현은 다음 순서로 진행한다.

1. 요청과 응답 모델을 정의한다.
2. 유스케이스 입력과 출력을 정의한다.
3. 필요한 포트 인터페이스를 정의한다.
4. 인프라 어댑터를 연결한다.
5. 라우터에서 유스케이스를 호출한다.
6. 테스트와 수동 검증을 수행한다.

라우터는 얇게 유지한다. 라우터가 직접 파일 처리, AI 호출, 데이터 조합, 리스크 판정 로직을 담당하지 않게 한다.

### 6. 검증

PR을 올리기 전에 최소 검증을 수행한다.

- 변경 파일 목록 확인
- 문서나 코드에 임시 표현이 남아 있지 않은지 확인
- 관련 테스트 실행
- 실행하지 못한 테스트가 있다면 이유를 기록
- API 계약이 이슈의 목표와 충돌하지 않는지 확인

문서 작업은 미완성 표시, 임시 표현, 채워 넣기 문구가 남아 있지 않은지 검색해 확인한다. 검색 결과가 없으면 문서가 완료 가능한 상태라고 본다.

### 7. 리뷰와 머지

작업 브랜치에서 `develop`으로 PR을 연다.

PR에는 다음 내용을 포함한다.

- 연결된 이슈 번호
- 변경 이유
- 주요 변경 사항
- 검증 명령과 결과
- 남은 리스크 또는 후속 작업

CodeRabbit 같은 리뷰 봇의 코멘트는 그대로 수용하지 않고, 실제 요구사항과 코드 흐름에 맞는지 확인한 뒤 반영한다.

### 8. 완료 처리

PR이 `develop`에 머지되면 다음을 정리한다.

- GitHub Project 상태가 `Done`인지 확인
- 원격 작업 브랜치 삭제
- 로컬 작업 브랜치 삭제
- 후속 작업이 있으면 새 이슈로 분리

## 완료 기준

백엔드 작업은 다음 조건을 만족할 때 완료로 본다.

- 이슈의 목표와 범위가 충족되었다.
- API 계약 또는 문서 계약이 명확하다.
- 변경 범위에 맞는 테스트 또는 수동 검증 증거가 있다.
- 남은 리스크가 있으면 PR에 기록했다.
- 작업 브랜치가 PR을 통해 `develop`에 반영되었다.
